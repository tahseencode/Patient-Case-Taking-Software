# MediKiosk / AyurKiosk — AI‑Powered Digital Clinical Intake Platform

**SIH26047** — An AI-powered digital clinical intake platform built for Indian OPD (Out‑Patient Department) and AYUSH institutions. Patients complete a guided, multilingual self‑intake at a kiosk before seeing a doctor; the platform structures that intake into a clinical summary, flags emergency red‑flags in real time, and pushes an ABDM‑compliant FHIR record for the physician.

## What it does

The platform models a full OPD patient journey in three stages:

1. **Kiosk self‑intake (patient‑facing):** Patient registers (with optional ABHA/ABDM ID), gives DPDP‑2023 digital consent, picks a chief complaint in their own language, answers a structured **SOCRATES** symptom questionnaire (Site, Onset, Character, Radiation, Associations, Timing, Exacerbating/relieving factors, Severity), and can have prior prescriptions/lab reports digitized (simulated OCR).
2. **AYUSH intake (optional stream):** For patients routed to the Ayurveda stream, a **Prakriti (body-constitution) questionnaire** computes a Vata/Pitta/Kapha score and derived Ayurvedic assessment (Agni, Koshtha, Sara, etc.).
3. **Doctor's OPD desk:** Physicians see a live OPD queue and real‑time emergency triage alerts, review the AI‑generated structured clinical summary (with ICD‑10 / AYUSH NAMASTE code suggestions), edit/finalize it, then complete the consultation with a diagnosis and prescription — which generates an ABDM FHIR R4 bundle for the patient's health record.

Real‑time updates (queue changes, triage alerts) are broadcast over a WebSocket (`/ws/live-feed`).

## Architecture

- **Backend:** Python, [FastAPI](https://fastapi.tiangolo.com/), served by `uvicorn`. All business logic lives in rule‑based/offline "engines" (no LLM required to function).
- **Frontend:** Static HTML/CSS/vanilla JS (no build step, no framework/bundler).
- **Data storage:** Persistent SQLite relational database (`backend/app/database/patient_intake.db`) with Write-Ahead Logging (WAL), foreign key constraints, DPDP audit trails, and ANSI SQL schema (`schema.sql`). All data persists across server restarts.
- **Serving model:** The FastAPI app itself mounts the `frontend/` folder as static files, so one process serves both the API and the UI.

```
Browser (kiosk / doctor desk)
        │  HTTP + WebSocket
        ▼
FastAPI app (backend/main.py)
  ├─ /api/v1/kiosk/*      → patient self-intake flow
  ├─ /api/v1/ayush/*      → Ayurvedic Prakriti assessment
  ├─ /api/v1/documents/*  → prescription/lab report digitization (simulated OCR)
  ├─ /api/v1/doctor/*     → OPD queue, triage alerts, consultation completion
  ├─ /api/v1/abdm/*       → ABHA verification, FHIR bundle, DPDP consent audit, stats
  ├─ /ws/live-feed        → WebSocket broadcast channel
  └─ /                    → serves frontend/ (index.html, app.html, etc.)
```

## Setup & running locally

```bash
# 1. Clone
git clone https://github.com/tahseencode/Patient-Case-Taking-Software.git
cd Patient-Case-Taking-Software

# 2. (Recommended) create a virtual environment
python -m venv venv
source venv/bin/activate       # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install -r backend/requirements.txt

# 4. Run the server — from the project ROOT, not from inside backend/
python -m backend.main
```

The app starts at **http://localhost:8000**:

| URL | What you get |
|---|---|
| `http://localhost:8000/` | Patient kiosk UI (`index.html`) |
| `http://localhost:8000/app.html` | Doctor / OPD desk UI |
| `http://localhost:8000/docs` | Interactive Swagger/OpenAPI docs (auto-generated by FastAPI) |
| `http://localhost:8000/redoc` | ReDoc API docs |
| `http://localhost:8000/api/health` | Health check |

> **Why run from the project root:** `main.py` imports its own routes as `backend.app.*` and mounts the frontend using a path relative to its own file location (`../frontend`). Running `uvicorn main:app` from inside `backend/` will break both.

`uvicorn.run(..., reload=True)` is set in `main.py`, so the server auto-reloads on code changes during development.

## Configuration

All settings live in `backend/app/core/config.py` and have sensible defaults — **no `.env` file or environment setup is required to run the app.**

| Setting | Default | Purpose |
|---|---|---|
| `APP_NAME` | `MediKiosk - AI Clinical Intake Platform` | Shown in `/api/health` and FastAPI docs |
| `API_PREFIX` | `/api/v1` | Prefix for all REST routes |
| `ABDM_FACILITY_ID` | `IN-AIIMS-DELHI-0012` | Simulated facility ID used in ABDM/FHIR responses |
| `ABDM_HIE_CM_URL` | `https://hie-cm.abdm.gov.in` | Reference URL for the (simulated) ABDM Health Information Exchange |
| `DPDP_CONSENT_VERSION` | `DPDP-ACT-2023-V1.4` | Version tag stamped on consent artifacts |
| `DEFAULT_LANGUAGE` | `hi` (Hindi) | Default UI/dialogue language |
| `GEMINI_API_KEY` / `OPENAI_API_KEY` | empty | **Optional.** The rule-based dialogue/triage/OCR engines work fully offline without these; they're placeholders for future LLM-assisted features. |

To override the optional keys, export them before starting the server:

```bash
export GEMINI_API_KEY="your-key-here"
```

## Core engines

These live under `backend/app/core/` and contain all the "intelligence" — all rule-based and deterministic, with no external API calls required:

- **`dialogue_engine.py`** — Master list of chief complaints (mapped to body part/specialty, with high-risk flags) in 8 Indian languages, plus the SOCRATES question sequence and basic transcript parsing.
- **`triage_detector.py`** — Rule-based red-flag detection (e.g., cardiac symptoms with radiation to arm/jaw) that assigns a `TriageLevel` (e.g., GREEN/YELLOW/RED) and severity score.
- **`ayush_engine.py`** — Prakriti questionnaire and Vata/Pitta/Kapha scoring logic for the AYUSH stream.
- **`ocr_engine.py`** — Simulates OCR/document digitization of prescriptions and lab reports, including a reference-range table for common Indian lab tests (e.g., HbA1c, FBS) to flag abnormal values.
- **`summarizer.py`** — Assembles the structured clinical summary (HPI, past history, medications, investigations) and maps chief complaints to ICD‑10 codes and AYUSH NAMASTE codes.
- **`fhir_builder.py`** — Builds an ABDM-style FHIR R4 `Bundle` (Composition, Patient, Condition, etc.) from a session's summary and consultation record.
- **`consent_manager.py`** — Creates a DPDP‑2023 consent artifact with a SHA‑256 hash for auditability.

## Data model

Defined in `backend/app/models/schemas.py` as Pydantic models, including `PatientDemographics`, `DPDP2023Consent`, `SocratesResponse`, `AyushPariksha`, `TriageAlert`/`TriageLevel`, `DocumentDigitization` (+ `ExtractedMedication`, `ExtractedLabInvestigation`), `StructuredClinicalSummary`, `DoctorConsultationRecord`/`DoctorPrescriptionItem`, and `IntakeSession` (the top-level object tying a patient's whole journey together).

## Relational SQL Database & Schema

All clinical intake records, patient profiles, consents, documents, and consultations persist in a real **SQLite relational database** (`backend/app/database/patient_intake.db`) with:
- **Write-Ahead Logging (WAL mode)** for high concurrency across kiosk terminals and doctor desks.
- **Foreign Key Enforcement (`PRAGMA foreign_keys = ON`)** for strict referential integrity.
- **ANSI SQL DDL (`backend/app/database/schema.sql`)** with 9 normalized tables:

| Table | Purpose | Primary Key | Foreign Keys |
|---|---|---|---|
| `patients` | Patient demographics, contact info, ABHA IDs, stream | `patient_id` | - |
| `consents` | DPDP 2023 digital consent artifacts, SHA-256 hashes | `consent_id` | `patient_id` → `patients` |
| `intake_sessions` | Clinical encounters, SOCRATES data, AYUSH, triage | `session_id` | `patient_id`, `consent_id` |
| `clinical_summaries` | Synthesized clinical narratives, ICD-10, NAMASTE | `summary_id` | `session_id`, `patient_id` |
| `documents` | Digitized OCR prescriptions & lab reports | `document_id` | `session_id`, `patient_id` |
| `consultations` | Doctor diagnoses, prescriptions, ABDM FHIR bundle IDs | `consultation_id` | `session_id`, `patient_id` |
| `opd_queue` | Active waiting line with triage priority and token | `id` (Auto) | `session_id` → `intake_sessions` |
| `triage_alerts` | Real-time red flag emergency notifications | `id` (Auto) | - |
| `audit_logs` | Immutable ABDM / DPDP compliance audit trails | `log_id` (Auto) | `patient_id`, `session_id` |

### Database CLI Utility

A command-line administration tool is provided in `backend/app/database/init_db.py`:

```bash
# Check database health, size, and table row counts:

# Re-initialize schema from schema.sql:
```

- **`GET /api/v1/database/tables`** — Lists all relational tables and their current record counts.

## Compliance notes

This is a **simulation/demo platform** built for a hackathon (Smart India Hackathon, problem statement SIH26047). It references real Indian healthcare standards and terminology — **ABDM** (Ayushman Bharat Digital Mission), **ABHA** IDs, **FHIR R4** bundles, and the **DPDP Act 2023** — but:

- ABHA verification (`/abdm/verify-abha`) is randomly generated/simulated, not a real call to the ABDM network.
- FHIR bundles are built locally and are not submitted to any live Health Information Exchange.
- Hospital statistics (`/abdm/hospital-stats`) mix hardcoded baseline numbers with live session counts for demo purposes.

Do not treat this as production-ready clinical or compliance software without a real integration review.

## Known limitations

- **No authentication/authorization:** any client can call any endpoint (CORS is wide open, `allow_origins=["*"]`).
- **No real OCR:** document "digitization" processes text you already provide (or a bundled sample) rather than reading an actual scanned image/PDF.
- **Single-node deployment:** SQLite is optimized for single-server or edge kiosk hardware; multi-node clusters can point `DATABASE_URL` to PostgreSQL.
